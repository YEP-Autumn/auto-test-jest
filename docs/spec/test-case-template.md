# 测试用例描述规范与模板

用例描述面向**人和任意执行手段**：只依据本文档就能手工复现，也可以用任何自动化框架落地。
因此文档里不出现任何测试框架、脚本或工具的实现细节。

使用方式：先按本模板写用例描述，评审通过后再落地脚本。

## 写作原则

1. 只写「做什么、观察到什么」，不写「用哪个类/方法/接口去做」。
2. 命令只用**被测设备的命令行**；不写代码、变量、断言表达式、正则、匹配模式。
3. 每条预期结果都能被独立判定：人能看懂，程序也能判定。
4. 一份用例控制在一到两屏；配置全量清单属于配套资料，不塞进用例正文。

## 禁止出现的内容

- 测试框架、库、工具、API、类/函数/方法名（如 `TestHelper`、`pytest`、`fixture`、`assert`、`expect`、`sleep()`）；
- 代码片段、变量名、调用语句、匹配模式与正则；
- 具体脚本路径与行号、脚本中的分组/标题结构（脚本对应关系放在「关联」元数据里即可）；
- 「调用 XX 完成 YY」这类实现视角的句子，一律改写为「在设备上执行…并确认…」。

> 注意：**被测设备的 CLI 命令必须写全**（这是手工执行的依据），被禁止的是用代码/方法调用来代替命令。

---

## 1. 基本信息

逐行列出（比单行宽表更适合窄窗口）：

- 用例编号：
- 用例标题：
- 所属特性：
- 级别 / 类型：
- 执行方式：手工 / 自动化
- 预估耗时：
- 关联：需求号或自动化脚本路径（仅追溯）

标题用中文陈述句，不加 `******`、`一、` 等装饰字符。

## 2. 组网与拓扑

1. **拓扑图**：只画本用例涉及的设备与连接，标注接口与网段。
   - **保持窄幅**：单行不超过 60 个字符，避免窄窗口下折行错位；
   - 图内不要混用中文字符（中文占两列会破坏对齐），说明文字放在图外；
   - 画不下时改用「链路列表」形式，每行一条链路：`A端设备.端口 -- 网段 -- B端设备.端口`。
2. **端口/地址表**：

   | 设备 | 接口/对象 | 所属 VRF | 地址或取值 | 连接对端 | 用途 |
   | --- | --- | --- | --- | --- | --- |

3. **协议与业务参数**：VRF（RD/RT/VNI）、AS、VLAN 等，用短列表集中写。
4. **说明**：未使用的端口/设备、跨 VRF 复用的网段等，一句话带过，避免被当成遗漏或笔误。

接口名用逻辑名（如 PortA）并注明「实际接口以组网为准」。

## 3. 预置条件

- 设备与连接：型号/数量、接口对应关系、链路介质；
- 初始状态：执行前设备应处于的配置状态（如接口为二层默认态、无残留 VRF/BGP/路由）；
- 环境：登录方式（console/telnet/ssh）、软件版本、许可证、是否需要终端或测试仪；
- 现场保留：失败时是否保留现场以便定位。

## 4. 测试步骤与预期结果

核心章节。按「初始检查 → 配置 → 触发与等待 → 校验」顺序组织，**每一步都必须给出可直接执行的命令列表**。

统一格式（外层用四个反引号，避免与命令块嵌套冲突）：

````
### 步骤 N：<动作标题>

<设备>：
```
<命令 1>
<命令 2>
...
```

**预期结果**：<可判定的现象>
````

写法约定：

- **命令列表必须完整可执行**：进入配置模式的入口命令、缩进的下级命令、返回命令都要给出；
  一条命令一行，按设备分组，可整块粘贴。
- 接口/IP 等实例值可用占位符（如 `<PortA>`、`<vrf>`），但必须说明占位符含义与替换规则。
- **命令只使用被测设备 CLI**，不写任何封装该命令的方法、参数或调用形式。
- **初始检查步**给出查看类命令（接口、路由、邻居、隧道等），预期为「无残留 / 默认态」。
- **等待步**写清原因与条件，优先「等待条件满足（如邻居 Up、路由出现）」，而不是固定时长；
  若使用固定时长，需说明依据；等待期间用于确认的命令一并列出。
- **校验步**除命令外必须给可判定的判据，并考虑误匹配（例如丢包率 0% 不能把 100% 当作通过）；
  可附「辅助确认」命令，用于定位失败原因。
- **含中文的对照关系（命令 → 预期）用表格或列表表达**，不要塞进代码块靠空格对齐。
- **打流/抓包步**写明报文特征（五元组、VLAN/VNI）、发包数量或时长、丢包/命中判据。
- 步骤较多时按「1.1 / 1.2」分组，每个分组块结尾给预期结果。

### 判定标准

一段话说明 Pass/Fail：哪几步必须无报错、哪些观测值必须满足、清理失败是否计入。

## 5. 清理与恢复

按安全顺序列出要删除/恢复的对象（一般：业务路由 → 接口/隧道/loopback → 协议 → VRF → 接口回二层），
**逐条给出可执行的命令列表**，并说明恢复后用哪些命令确认已回到初始状态。

## 6. 备注 / 待确认

一行一条：歧义点、冗余配置、可疑步骤、可选优化。脚本与描述不一致处必须写在这里。

## 编写自检清单

1. 通篇没有出现框架、工具、函数、代码、匹配模式？
2. 没写过脚本的人只看本文档能否手工执行？
3. **每一步是否都有完整、可直接粘贴的命令列表？占位符是否已说明？**
4. 每条预期结果都能判定，且不易误判？
5. 等待是否有理由，能否改为等条件满足？
6. 清理是否覆盖全部新增对象、给出命令、顺序是否安全？
7. 跨 VRF/全局复用的网段、未使用的端口是否已说明？
