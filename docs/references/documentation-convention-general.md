# 文档编写规范（通用版）

## 1. 目的与适用范围

### 1.1 目的

统一文档的书面表达、术语和结构，使读者能够准确理解规则，并按文档完成操作。

### 1.2 适用范围

本规范适用于各类说明性文档，包括：

- 项目说明与入门指南；
- 规范、约定与流程文档；
- 操作指南、部署与运维手册；
- 接口、参数、配置项等参考资料；
- 记录执行结果与问题的报告类文档。

代码注释、提交信息、脚本等按其各自规范执行；本规范仅约束说明性文字。

### 1.3 文档类型

| 类型 | 用途 | 写作重点 |
| --- | --- | --- |
| 规范 | 约定必须遵守的规则 | 要求明确、判据可执行、例外可追溯 |
| 指南 | 说明操作方法与流程 | 步骤完整、命令可执行、结果可验证 |
| 参考 | 汇总参数、字段、接口或清单 | 分类清晰、取值准确、更新及时 |
| 记录 | 记录执行结果与问题 | 时间、对象、现象、结论、证据完整 |

## 2. 基本原则

### 2.1 使用书面语

文档使用规范书面语；口语、网络用语、语气词和情绪化表达改写为书面表达。

| 场景 | 推荐写法 |
| --- | --- |
| 表达操作 | 执行、编写、配置、校验、记录 |
| 表达要求 | 应、须、需要 |
| 表达建议 | 建议、推荐、优先 |
| 表达结果 | 完成、通过、失败、符合要求 |
| 表达问题 | 缺陷、风险、异常、偏差 |

### 2.2 使用陈述句

文档使用陈述句表达规则、步骤和结论；反问句、设问句和自问自答式表达改写为陈述句。下表左列为待改写示例，仅用于对照；正文使用右列写法。

| 原表达 | 推荐表达 |
| --- | --- |
| 为什么要执行这一步？ | 该步骤用于初始化运行环境。 |
| 如何配置超时时间？ | 超时时间的配置方法如下。 |
| 哪个参数控制并发数？ | `concurrency` 参数控制并发数。 |
| 日志保存在哪里？ | 日志保存在文档约定的输出目录中。 |

### 2.3 明确执行主体与动作

每条操作说明写明执行主体、动作、对象、条件和结果。连续步骤可省略主语，其余规则句写明执行主体。

| 原表达 | 推荐表达 |
| --- | --- |
| 需要处理一下残留数据。 | 维护人员应删除残留数据。 |
| 配置完成后检查状态。 | 配置完成后，执行人员应检查服务状态。 |
| 有问题时查看日志。 | 任务失败时，执行人员应保存日志并记录失败步骤。 |

### 2.4 优先使用正向表达

文档优先说明应执行的动作和允许的范围。需要限制时，写明限制条件与替代做法。

| 原表达 | 推荐表达 |
| --- | --- |
| 不要使用相对路径导入。 | 导入统一使用项目约定的别名。 |
| 不能跳过清理步骤。 | 清理步骤应覆盖全部新增对象。 |
| 不要写无信息量的标题。 | 标题应包含改动对象与动作。 |
| 禁止空标题。 | 标题必须非空。 |

### 2.5 使用明确的量词与条件

文档给出具体数值、单位、范围和触发条件；模糊量词和主观评价改写为量化描述。

| 原表达 | 推荐表达 |
| --- | --- |
| 尽量缩短等待时间。 | 等待时间不超过 30 秒。 |
| 执行较快。 | 单次执行耗时约 2 分钟。 |
| 配置若干参数。 | 配置主机地址、端口和认证信息。 |
| 必要时保留现场。 | 任务失败且需要定位时，保留现场并记录路径。 |

### 2.6 统一术语

同一概念在全文使用同一术语。首次出现的缩写应给出中文名称与英文原文。

| 概念 | 统一用语 | 原表达 |
| --- | --- | --- |
| 执行任务 | 运行、执行 | 跑一下、走一遍 |
| 软件缺陷 | 缺陷 | bug |
| 代码评审 | 评审 | review |
| 后续维护人员 | 后续维护人员 | 后来者 |
| 命令回显 | 回显 | 输出内容（存在歧义时） |
| 配置文件 | 配置文件 | 配置（指代不清时） |

### 2.7 先结论后细节

段落首句说明结论或目的，后续句子给出依据、步骤和示例。长段落按主题拆分，每个段落仅表达一个主题。

## 3. 用词规范

### 3.1 推荐用语

| 场景 | 推荐用语 | 说明 |
| --- | --- | --- |
| 强制要求 | 应、须 | 用于必须遵守的规则 |
| 推荐做法 | 建议、推荐、优先 | 用于可选择的更优做法 |
| 操作动作 | 执行、编写、配置、校验、记录、删除、恢复 | 使用动词开头的陈述句 |
| 说明内容 | 写明、给出、标注、列出、注明 | 明确需要补充的信息 |
| 表达结果 | 通过、失败、符合要求、存在偏差 | 使用可判定的结果词 |
| 表达目的 | 用于、以便、确保、保持 | 说明动作的目的或效果 |

### 3.2 用词对照与替换

下表列出常见口语化、模糊化表达及推荐替换。左列为待改写示例，仅用于对照；正文使用右列写法，并结合上下文调整句式。

| 原表达 | 推荐表达 | 说明 |
| --- | --- | --- |
| 一眼看出 | 清晰呈现、便于识别 | 说明读者能够快速定位信息 |
| 便于后来者 | 便于后续维护人员 | 明确人员范围 |
| 不要自造 | 使用约定的取值 | 说明允许的取值范围 |
| 长得一样 | 结构统一 | 说明一致性要求 |
| 骨架 | 结构 | 使用规范术语 |
| 落地 | 编写、实现、发布 | 根据上下文选择具体动作 |
| 怎么、如何 | 方法、步骤、规范 | 标题使用名词短语，正文使用陈述句 |
| 什么、哪、第几 | 具体对象、具体编号 | 直接写明对象或编号 |
| 为什么不 | 陈述句 | 直接说明原因、范围或结论 |
| 请、务必、注意 | 应、需要、说明 | 使用规范要求用语 |
| 只 | 仅 | 使用书面量词 |
| 一下 | 删除，或写明具体动作 | 使用具体动作 |
| 比如 | 例如 | 使用书面举例用语 |
| 尽量、最好 | 建议、优先、在条件 X 下 | 写明条件或优先级 |
| 差不多、大概 | 约、在……范围内 | 给出数值或范围 |
| 其实、当然 | 删除 | 不承载信息 |
| 搞、弄 | 执行、处理、配置 | 使用具体动词 |
| 写死 | 固定为、硬编码 | 使用技术术语 |
| 坑、踩坑 | 问题、风险、注意事项 | 使用规范术语 |
| 抄 | 复用、参考 | 说明来源与方式 |
| 塞进 | 放入、写入 | 使用具体动作 |
| 搬 | 迁移、移动 | 使用具体动作 |
| 省事、省时间 | 减少操作步骤、提高效率 | 说明具体收益 |
| 顺手 | 同时、一并 | 说明动作关系 |
| 一键 | 执行一次、通过一条命令 | 说明操作方式 |
| 很好、非常 | 删除，或给出量化指标 | 使用量化指标 |
| 呢、吧、啊、嘛 | 删除 | 使用陈述句 |
| 我们、你 | 删除，或使用执行人员、维护人员 | 使用明确主体 |

### 3.3 术语大小写与格式

- 代码标识、命令、路径、参数名使用反引号包裹，例如 `timeout`、`git status`、`config/settings.json`。
- 标准编号使用正式写法，例如 ISO 8601、RFC 2119、UTF-8。
- 缩写首次出现时给出中文名称与英文原文，例如“持续集成（Continuous Integration，CI）”。
- 中文与英文、数字之间保留一个空格，例如“配置 2 个实例”“执行 `git status`”。

## 4. 句式规范

### 4.1 规则句

规则句使用“主体 + 应/须 + 动作 + 对象 + 条件”的结构。

示例：

- 维护人员应在提交前执行代码检查。
- 任务失败时，执行人员应保存日志与失败截图。
- 配置变更后，执行人员应重新执行受影响的校验。

### 4.2 步骤句

步骤句使用“先……，再……，最后……”或连续编号。每个步骤仅包含一个动作。

示例：

1. 打开配置文件。
2. 填写连接地址与认证信息。
3. 保存文件并重启服务。

### 4.3 条件句

条件句使用“当……时，应……”或“在……条件下，使用……”。条件与结果写在同一句中。

示例：

- 当校验结果不符合预期时，停止后续流程。
- 在依赖版本冲突时，将任务状态标记为 `Blocked`。

### 4.4 判定句

判定句写明对象、判据、比较方向和单位。

示例：

- 错误率应为 0%。
- 响应时间应小于或等于 1 秒。
- 重试次数应增加至少 1。
- 输出中应包含 `success`。

### 4.5 示例句

示例使用“示例：”引出，并与正文规则一致。推荐示例与待调整示例分别标注。

- 推荐示例：`标题应包含改动对象与动作。`
- 待调整示例：`标题写清楚一点。`

## 5. 结构规范

### 5.1 标题

- 一级标题使用文档名称。
- 二级、三级标题使用名词短语，例如“适用范围”“用词规范”“评审清单”。
- 标题中的问句、感叹句和装饰字符改写为名词短语。
- 标题层级连续递进，不跳级。

### 5.2 段落

- 每个段落仅表达一个主题。
- 段落首句说明结论或目的。
- 段落长度建议不超过 5 行。
- 并列内容使用列表或表格分项呈现。

### 5.3 列表

- 操作步骤使用有序列表。
- 条件、选项、检查项使用无序列表。
- 每个列表项结构一致，首字词性一致。
- 列表项统一使用或统一省略句号。

### 5.4 表格

- 表格包含表头行与分隔行。
- 每行列数一致。
- 一行仅描述一个对象或一组对应关系。
- 表头写明字段含义与单位。
- 表格内容使用短句分项呈现。

### 5.5 代码块

- 代码块标注语言类型，例如 `bash`、`json`、`yaml`、`text`。
- 命令块给出完整、可直接执行的命令。
- 占位符使用 `<host>`、`<port>` 等格式，并在正文说明替换规则。
- 代码块内保持完整可复制，避免中间插入说明文字。
- 示例代码与正文规则一致。

### 5.6 链接

- 仓库内文档使用相对链接。
- 链接文字说明目标文档或章节名称。
- 修改文档后检查链接目标是否存在。
- 外部链接使用完整 URL。

### 5.7 图

- ASCII 图使用等宽字符，单行宽度建议不超过 80 个字符。
- 图中仅使用 ASCII 字符，说明文字放在图外。
- 图后给出图注或字段说明。

## 6. 内容要求

### 6.1 信息完整

文档包含读者执行操作所需的信息：

- 操作对象；
- 前置条件；
- 操作步骤；
- 预期结果；
- 异常处理；
- 清理与恢复；
- 关联文档。

### 6.2 数据准确

- 数值给出单位，例如 30 秒、1000 条、4094 字节。
- 范围写明上下限，例如“取值范围为 1 至 4094”。
- 时间写明时区或基准，例如“以 UTC 时间为准”。
- 版本写明适用版本，例如“适用于 v1.2.0 及以上版本”。

### 6.3 表述一致

- 同一对象在全文使用同一名称。
- 同一操作在全文使用同一动词。
- 同一判据在全文使用同一单位与比较方向。
- 表格、列表、正文中的术语保持一致。

### 6.4 使用可验证指标

文档使用可验证的指标；“简单”“容易”“快速”“稳定”“强大”等主观评价词改写为量化描述。

| 原表达 | 推荐表达 |
| --- | --- |
| 配置过程很简单。 | 配置过程包含 3 个步骤。 |
| 该方案性能很好。 | 该方案处理 1000 条记录耗时 10 秒。 |
| 命令执行较快。 | 命令平均响应时间为 200 毫秒。 |

### 6.5 精简修饰词

正文保留承载信息的修饰词；程度描述使用具体数值，例如用“响应时间为 200 毫秒”替代“非常快”。

## 7. 评审清单

文档提交前，按以下清单逐项检查：

1. 全文使用规范书面语；口语、网络用语和语气词已改写为书面表达。
2. 标题使用名词短语；反问句、设问句和装饰字符已改写为名词短语。
3. 每条规则写明执行主体、动作、对象、条件和结果。
4. 限制性规定写明允许范围或替代做法。
5. 同一概念使用同一术语，缩写首次出现时已定义。
6. 数值、单位、范围和条件明确。
7. 表格列数一致，代码块标注语言类型，链接目标有效。
8. 示例与正文规则一致，命令可直接执行。
9. 正文使用具体数值、范围或条件，替代“若干”“一些”“尽量”“最好”“大概”等模糊表达。
10. 正文使用执行人员、维护人员等明确主体，替代“我们”“你”等人称代词。
11. 文档与当前实现、配置和目录结构一致。
12. 修改文档后，检查相关文档中的引用与链接。

## 8. 修改流程

1. 确认修改范围与受影响文档。
2. 按本规范修改正文、表格、代码块与链接。
3. 执行第 7 节评审清单。
4. 提交评审，记录修改原因与影响范围。
5. 评审通过后合并，并同步更新相关引用。
