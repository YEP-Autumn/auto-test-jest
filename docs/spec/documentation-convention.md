# 文档编写规范

## 0. 修订背景

本轮文档整理统一了以下表达方式：

- 口语化表达改为书面语；
- 反问句、设问句改为陈述句；
- 模糊指代改为明确对象；
- 否定式限制改为正向指引；
- 同一概念统一使用同一术语；
- 操作步骤写明执行主体、动作、对象、条件与结果。

本规范将上述规则固化为文档编写要求，适用于 `docs/**`、`README.md` 及仓库内的说明性文档。

## 1. 目的与适用范围

### 1.1 目的

统一文档的书面表达、术语和结构，使读者能够准确理解规则，并按文档完成操作。

### 1.2 适用范围

本规范适用于以下文档：

- `README.md`；
- `docs/spec/**` 下的规范与约定；
- `docs/test-cases/**` 下的用例描述；
- 其它面向维护人员、测试人员或使用人员的说明性文档。

代码注释、提交信息和测试脚本按各自规范执行：提交信息遵循
[`commit-convention.md`](commit-convention.md)，测试脚本遵循
[`test-script-convention.md`](test-script-convention.md)，用例命名遵循
[`naming-convention.md`](naming-convention.md)，用例设计遵循
[`test-case-template.md`](test-case-template.md)。

### 1.3 文档类型

| 类型 | 用途 | 写作重点 |
| --- | --- | --- |
| 规范 | 约定必须遵守的规则 | 要求明确、判据可执行、例外可追溯 |
| 指南 | 说明操作方法与流程 | 步骤完整、命令可执行、结果可验证 |
| 参考 | 汇总参数、字段、接口或清单 | 分类清晰、取值准确、更新及时 |
| 记录 | 记录执行结果与问题 | 时间、对象、现象、结论、证据完整 |

## 2. 基本原则

### 2.1 使用书面语

文档使用规范书面语；口语、网络用语、语气词和情绪化表达改写为书面表达。

| 场景 | 推荐写法 |
| --- | --- |
| 表达操作 | 执行、编写、配置、校验、记录 |
| 表达要求 | 应、须、需要 |
| 表达建议 | 建议、推荐、优先 |
| 表达结果 | 完成、通过、失败、符合要求 |
| 表达问题 | 缺陷、风险、异常、偏差 |

### 2.2 使用陈述句

文档使用陈述句表达规则、步骤和结论；反问句、设问句和自问自答式表达改写为陈述句。
表中左列为待改写示例，仅用于对照；正文使用右列写法。

| 原表达 | 推荐表达 |
| --- | --- |
| 为什么不使用托管 runner？ | 设备用例由自托管 runner 执行。 |
| 如何配置 VLAN？ | VLAN 配置步骤如下。 |
| 哪个参数控制超时？ | `timeout` 参数控制超时时间。 |
| 第几条用例覆盖该场景？ | 用例 0010 覆盖该场景。 |

### 2.3 明确执行主体与动作

每条操作说明写明执行主体、动作、对象、条件和结果。连续步骤可省略主语，其余规则句写明执行主体。

| 原表达 | 推荐表达 |
| --- | --- |
| 需要处理一下残留配置。 | 维护人员应删除残留配置。 |
| 配置完成后检查状态。 | 配置完成后，执行 `show` 命令检查协议状态。 |
| 有问题时查看日志。 | 用例失败时，执行人员应保存日志并记录失败步骤。 |

### 2.4 优先使用正向表达

文档优先说明应执行的动作和允许的范围。需要限制时，写明限制条件与替代做法。

| 原表达 | 推荐表达 |
| --- | --- |
| 不要使用相对路径导入。 | 导入统一使用 `@/` 别名。 |
| 不能跳过清理步骤。 | 清理步骤应覆盖全部新增对象。 |
| 不要写无信息量的标题。 | 标题应包含改动对象与动作。 |
| 禁止空标题。 | 标题必须非空。 |

### 2.5 使用明确的量词与条件

文档给出具体数值、单位、范围和触发条件；模糊量词和主观评价改写为量化描述。

| 原表达 | 推荐表达 |
| --- | --- |
| 尽量缩短等待时间。 | 等待时间不超过 30 秒。 |
| 用例执行较快。 | 单条用例执行时间约为 2 分钟。 |
| 配置若干参数。 | 配置 Router ID、Area 和认证参数。 |
| 必要时保留现场。 | 用例失败且需要定位时，保留现场并记录路径。 |

### 2.6 统一术语

同一概念在全文使用同一术语。首次出现的缩写应给出中文名称与英文原文。

| 概念 | 统一用语 | 原表达 |
| --- | --- | --- |
| 执行测试 | 执行用例 | 跑用例、跑测试 |
| 发送流量 | 流量发送 | 打流 |
| 流量收发服务 | 流量收发后端 | 打流后端 |
| 测试仪 | 测试仪 | 打流仪 |
| 文件组织 | 文件结构 | 文件骨架 |
| 编写脚本 | 编写脚本 | 落地脚本 |
| 代码评审 | 评审 | review |
| 软件缺陷 | 缺陷 | bug |
| 后续维护人员 | 后续维护人员 | 后来者 |
| 命令回显 | 回显 | 输出内容（存在歧义时） |

### 2.7 先结论后细节

段落首句说明结论或目的，后续句子给出依据、步骤和示例。长段落按主题拆分，每个段落仅表达一个主题。

## 3. 用词规范

### 3.1 推荐用语

| 场景 | 推荐用语 | 说明 |
| --- | --- | --- |
| 强制要求 | 应、须 | 用于必须遵守的规则 |
| 推荐做法 | 建议、推荐、优先 | 用于可选择的更优做法 |
| 操作动作 | 执行、编写、配置、校验、记录、删除、恢复 | 使用动词开头的陈述句 |
| 说明内容 | 写明、给出、标注、列出、注明 | 明确需要补充的信息 |
| 表达结果 | 通过、失败、符合要求、存在偏差 | 使用可判定的结果词 |
| 表达目的 | 用于、以便、确保、保持 | 说明动作的目的或效果 |

### 3.2 用词对照与替换

下表列出常见口语化、模糊化表达及推荐替换。表中左列为待改写示例，仅用于对照；正文使用右列写法，并结合上下文调整句式。

| 原表达 | 推荐表达 | 说明 |
| --- | --- | --- |
| 一眼看出 | 清晰呈现、便于识别 | 说明读者能够快速定位信息 |
| 一句话说明 | 使用简洁陈述句概括 | 说明表达长度与形式 |
| 便于后来者 | 便于后续维护人员 | 明确人员范围 |
| 不要自造 | 使用本文登记的后缀 | 说明允许的取值范围 |
| 手工翻目录 | 按类型批量筛选 | 说明操作方式 |
| 长得一样 | 结构统一 | 说明一致性要求 |
| 跑用例、跑回归 | 执行用例、执行回归 | 使用书面动词 |
| 打流 | 流量发送 | 使用规范术语 |
| 骨架 | 结构 | 使用规范术语 |
| 落地 | 编写、实现、发布 | 根据上下文选择具体动作 |
| 怎么、如何 | 方法、步骤、规范 | 标题使用名词短语，正文使用陈述句 |
| 什么、哪、第几 | 具体对象、具体编号 | 直接写明对象或编号 |
| 为什么不 | 陈述句 | 直接说明原因、范围或结论 |
| 请、务必、注意 | 应、需要、说明 | 使用规范要求用语 |
| 只 | 仅 | 使用书面量词 |
| 一下 | 删除，或写明具体动作 | 使用具体动作 |
| 比如 | 例如 | 使用书面举例用语 |
| 尽量、最好 | 建议、优先、在条件 X 下 | 写明条件或优先级 |
| 差不多、大概 | 约、在……范围内 | 给出数值或范围 |
| 其实、当然 | 删除 | 不承载信息 |
| 搞、弄 | 执行、处理、配置 | 使用具体动词 |
| 写死 | 固定为、硬编码 | 使用技术术语 |
| 坑、踩坑 | 问题、风险、注意事项 | 使用规范术语 |
| 抄 | 复用、参考 | 说明来源与方式 |
| 塞进 | 放入、写入 | 使用具体动作 |
| 搬 | 迁移、移动 | 使用具体动作 |
| 省事、省时间 | 减少操作步骤、提高效率 | 说明具体收益 |
| 顺手 | 同时、一并 | 说明动作关系 |
| 一键 | 执行一次、通过一条命令 | 说明操作方式 |
| 很好、非常 | 删除，或给出量化指标 | 使用量化指标 |
| 呢、吧、啊、嘛 | 删除 | 使用陈述句 |
| 我们、你 | 删除，或使用执行人员、维护人员 | 使用明确主体 |

### 3.3 术语大小写与格式

- 代码标识、命令、路径、参数名使用反引号包裹，例如 `TestHelper`、`show vlan`、`config/profiles`。
- 标准编号使用正式写法，例如 IEEE 802.1Q、RFC 2328、ITU-T G.8032。
- 缩写首次出现时给出中文名称与英文原文，例如“被测设备（Device Under Test，DUT）”。
- 中文与英文、数字之间保留一个空格，例如“配置 2 个 VLAN”“执行 `npm run default`”。

## 4. 句式规范

### 4.1 规则句

规则句使用“主体 + 应/须 + 动作 + 对象 + 条件”的结构。

示例：

- 维护人员应在提交前执行 `npm run check`。
- 用例失败时，执行人员应保存回显与抓包文件。
- 配置变更后，测试人员应重新执行相关用例。

### 4.2 步骤句

步骤句使用“先……，再……，最后……”或连续编号。每个步骤仅包含一个动作。

示例：

1. 执行 `configure terminal` 进入配置模式。
2. 执行 `vlan 100` 创建 VLAN。
3. 执行 `end` 返回用户模式。

### 4.3 条件句

条件句使用“当……时，应……”或“在……条件下，使用……”。条件与结果写在同一句中。

示例：

- 当邻居状态为 `Full` 时，执行路由校验。
- 在设备能力不匹配时，将用例结论标记为 `Blocked`。

### 4.4 判定句

判定句写明对象、判据、比较方向和单位。

示例：

- 丢包率应为 0%。
- 收敛时间应小于或等于 1 秒。
- 协议计数应增加至少 1。
- 回显中应包含 `Established`。

### 4.5 示例句

示例使用“示例：”引出，并与正文规则一致。推荐示例与待调整示例分别标注。

示例：

- 推荐示例：`标题应包含改动对象与动作。`
- 待调整示例：`标题写清楚一点。`

## 5. 结构规范

### 5.1 标题

- 一级标题使用文档名称。
- 二级、三级标题使用名词短语，例如“适用范围”“用词规范”“评审清单”。
- 标题中的问句、感叹句和装饰字符改写为名词短语。
- 标题层级连续递进。

### 5.2 段落

- 每个段落仅表达一个主题。
- 段落首句说明结论或目的。
- 段落长度建议不超过 5 行。
- 并列内容使用列表或表格分项呈现。

### 5.3 列表

- 操作步骤使用有序列表。
- 条件、选项、检查项使用无序列表。
- 每个列表项结构一致，首字词性一致。
- 列表项以句号结尾时，全部列表项统一使用句号。

### 5.4 表格

- 表格包含表头行与分隔行。
- 每行列数一致。
- 一行仅描述一个对象或一组对应关系。
- 表头写明字段含义与单位。
- 表格内容使用短句分项呈现。

### 5.5 代码块

- 代码块标注语言类型，例如 `ts`、`bash`、`json`、`markdown`。
- 命令块给出完整、可直接执行的命令。
- 占位符使用 `<PortA>`、`<profile>` 等格式，并在正文说明替换规则。
- 代码块使用连续文本展示完整命令。
- 示例代码与正文规则一致。

### 5.6 链接

- 仓库内文档使用相对链接。
- 链接文字说明目标文档或章节名称。
- 修改文档后检查链接目标是否存在。
- 外部链接使用完整 URL。

### 5.7 图

- ASCII 图使用等宽字符，单行宽度建议不超过 80 个字符。
- 图中使用 ASCII 字符，说明文字放在图外。
- 图后给出图注或端口说明。

## 6. 内容要求

### 6.1 信息完整

文档包含读者执行操作所需的信息：

- 操作对象；
- 前置条件；
- 操作步骤；
- 预期结果；
- 异常处理；
- 清理与恢复；
- 关联文档。

### 6.2 数据准确

- 数值给出单位，例如 30 秒、1000 个、4094。
- 范围写明上下限，例如“取值范围为 1 至 4094”。
- 时间写明时区或基准，例如“以设备本地时间为准”。
- 版本写明适用版本，例如“适用于 V0.0.1”。

### 6.3 表述一致

- 同一对象在全文使用同一名称。
- 同一操作在全文使用同一动词。
- 同一判据在全文使用同一单位与比较方向。
- 表格、列表、正文中的术语保持一致。

### 6.4 使用可验证指标

文档使用可验证的指标；“简单”“容易”“快速”“稳定”“强大”等主观评价词改写为量化描述。

| 原表达 | 推荐表达 |
| --- | --- |
| 配置过程很简单。 | 配置过程包含 3 个步骤。 |
| 该方案性能很好。 | 该方案在 1000 条用例下执行时间为 10 分钟。 |
| 命令执行较快。 | 命令平均响应时间为 200 毫秒。 |

### 6.5 精简修饰词

正文保留承载信息的修饰词；程度描述使用具体数值，例如用“响应时间为 200 毫秒”替代“非常快”。

## 7. 评审清单

文档提交前，按以下清单逐项检查：

1. 全文使用规范书面语；口语、网络用语和语气词已改写为书面表达。
2. 标题使用名词短语；反问句、设问句和装饰字符已改写为名词短语。
3. 每条规则写明执行主体、动作、对象、条件和结果。
4. 限制性规定写明允许范围或替代做法。
5. 同一概念使用同一术语，缩写首次出现时已定义。
6. 数值、单位、范围和条件明确。
7. 表格列数一致，代码块标注语言类型，链接目标有效。
8. 示例与正文规则一致，命令可直接执行。
9. 正文使用具体数值、范围或条件，替代“若干”“一些”“尽量”“最好”“大概”等模糊表达。
10. 正文使用执行人员、维护人员等明确主体，替代“我们”“你”等人称代词。
11. 文档与当前实现、配置和目录结构一致。
12. 修改文档后，检查相关文档中的引用与链接。

## 8. 修改流程

1. 确认修改范围与受影响文档。
2. 按本规范修改正文、表格、代码块与链接。
3. 执行第 7 节评审清单。
4. 提交评审，记录修改原因与影响范围。
5. 评审通过后合并，并同步更新相关引用。
